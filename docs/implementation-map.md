# Карта реализации

Документ указывает реальные точки входа публичного кода и связи, которые нужно проверять при продолжении. Карта относится к [исследовательскому снимку `offline-completion-20261020`](https://github.com/gon7187/techstream/tree/offline-completion-20261020); основная ветка отдельно публикует документацию и граф. Само наличие модуля не означает полноту семейства, завершённую интеграцию или физическую поддержку автомобиля.

## Контракты между слоями

- **Идентичность источника.** Привязывать утверждение к точному исходнику, версии, хешу и RVA/контракту. Имя файла, alias, количество exports или похожая подпись не доказывают идентичность. Изменение зависимости требует узкой повторной проверки.
- **Владение ресурсом.** Один native address/context должен иметь одного опубликованного владельца. Алиасы не должны создавать параллельные managers. Ошибка создания или запуска должна оставлять очистку работоспособной; освобождение учитывает владельца и поколение ресурса.
- **Частичное состояние.** Различать отсутствующее, неподдерживаемое, некорректное, завершившееся ошибкой, отменённое и присутствующее значение. Не собирать успешный отчёт из одного поля, если полный контракт не выполнен.
- **Отмена и ошибки.** Сохранять контракт результата и первичную ошибку вызывающего кода, освобождать принадлежащие ресурсы и не перезаписывать актуальный общий статус устаревшим снимком.
- **HOST и native.** Явная host-реализация или внедрённый backend подтверждают только свой программный контракт. Они не доказывают Windows ABI, поведение OEM runtime, тайминги адаптера или ответ автомобиля. Маркировать source-only, host simulation, GUI rendering и physical evidence отдельно.
- **Незавершённые joins.** Реализованный helper не означает завершённый путь вызывающего кода. Проверять реального публичного потребителя: issuer → pool → execute context, кэш, bridge dispatch, вложенную идентичность utility-модуля, очередь и отчёт.
